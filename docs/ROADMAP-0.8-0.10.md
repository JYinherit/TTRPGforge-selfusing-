# ClueForge 地图工坊 · 未来 2–3 个迭代的技术路线与风险清单

- 日期：2026-10-29 ｜ 角色：CTO 视角（只定方向与代价，不写实现）
- 评审对象：标记备注/叠放顺序 · 光照与视野墙(LOS) · 可复用素材库 · 多楼层
- 结论先行：**排期顺序 = 备注+层序 → 素材库+多楼层 → LOS**。理由在 §4，压倒性理由只有一条：前三件的前置改动（版本策略、限额单一真源、统一重排）是后三件的地基，先做便宜三倍。

## 0. 业务约束复述（先对齐，再谈方案）

## 2. 议题一：标记备注 / 叠放顺序

业务问题：*摆完 tokens 以后，我要能在图上留一句"这里躺着个昏迷的调查员"，并且让"门压着 token"或"token 压着门"是我说了算，而不是每次重开图就变。*

### 2.1 备注

| | A 档：快 | B 档：对 |
| --- | --- | --- |
| 方案要点 | `MarkerMeta.note?: string`（≤2000 字）+ 检查器 textarea，失焦/停手 400ms 写回；可选"图上气泡"（`fabric.Textbox` + `cfNote` 标记，`collectDoc` 跳过），气泡只做显示 | 同一字段 + 备注进入搜索/筛选、导出 JSON 附 `notes` 摘要、备注支持 Markdown 子集（复用已打包的 `marked`，零新增依赖） |
| 上线时间 | 1.5–2 人日 | +3–4 人日 |
| 一次性成本 | 极低 | 低 |
| 每周期成本 | 快照变大（见 2.3 利息），可忽略 | 搜索索引需在 `loadDoc` 后重建 |
| 兼容风险 | **低，但有一坑**：`DOC_LIMITS` 必须新增 `noteChars: 2000`，不能沿用 `label` 的 40 字；否则表现为"写完保存了，重开没了"（F8 实锤的静默截断） | 同左 |
| 失败模式 | 每按键都 `pushHistory` → 撤销栈被打字灌满，Ctrl+Z 变成"删一个字" | — |
| 退出/迁移 | 纯增量字段，删除即回退 | — |

**备注是最便宜的高感知项**，没有理由不进第一个迭代。

### 2.2 叠放顺序

先说一个反直觉的判断：**这一步第一件事不是加 `z` 字段，而是消灭"层序漂移"**（F3/F4）。今天同一张图，"刚画的房间盖住标记"和"重开图后标记盖住房间"是两套顺序，用户感知为随机。把这条修掉（所有 `canvas.add` 收敛到一个 `applyZOrder()`），成本 0.5–1 人日，收益是"图看起来永远一样"。

| | A 档：快（推荐） | B 档：对 |
| --- | --- | --- |
| 方案要点 | ①固定层带：走廊 0 < 房间 100 < 墙 200 < 门 300 < 标记 400 < 覆盖层 900（与 FVTT 的 tiles/walls/tokens 心智一致）②标记上加可选 `z?: number`，值域 400–899，支持 上移/下移/置顶/置底 ③`applyZOrder()` 成为唯一重排入口，`docToObjects` / `swapMarkerImage` / `rebuildObject` / 批量拖动重建全部走它 | 真正的图层：`doc.layers: {id,name,order,visible,locked}` + 每个 meta 加 `layerId` + 图层面板 UI；跨类型自由叠放 |
| 上线时间 | 2–3 人日（含修漂移） | 8–12 人日 |
| 引入的技术债 | 跨类型叠放不支持（"让标记压在某面墙下"做不到）。**利息：0**（真实需求 90% 是标记之间/标记与门之间），除非有人要做"半透明的屋顶层" | 无 |
| 兼容风险 | 低。旧版打开会按类型序重排 → 用户看到的层序回退（不崩，见 ADR-001） | 中：图层面板会引出"隐藏层"语义，导出 PNG 是否含隐藏层必须定义，否则又是一次口径分叉 |
| 失败模式 | 只改 `docToObjects` 而漏改重建路径 → 层序"时好时坏"，比没有更坏 | 面板 UI 走 `lint-tokens` 门禁，样式硬编码会直接构建失败（好事，但要算进工期） |
| 退出/迁移 | 删 `z` 字段即回退；`applyZOrder` 保留（它修的是 bug） | 需 ADR 记"跨类型层"代价后才可上 |

**推荐 A 档**：本工具只有 5 类元素，层交叉的真实需求是"标记与门谁在上"，不值得为它引一套图层模型。`z` 用整数而非浮点：浮点分数索引（fractional indexing）在 JS 里省的是重排次数，而我们的重排本来就只有 60 层快照、500 个标记。

### 2.3 备注 + 层序的合并估价与利息

| 项 | 值 |
| --- | --- |
| 合计一次性成本 | **3.5–5 人日** |
| 新增数据 | `note?: string`、`noteVisible?: boolean`、`z?: number`（全部 optional） |
| 数据模型改动 | 仅 `types.ts` 加字段 + `DOC_LIMITS` 加 `noteChars`；`normalizeDoc` 加一行保留；`collectDoc` 无需改（它 `...clone(meta)` 会带过去） |
| 撤销栈利息 | 快照体积随备注增长：500 个标记 × 平均 200 字 ≈ 100KB/快照 × 60 层 ≈ 6MB 常驻内存。**触发还债信号：`pushHistory` 单次 > 30ms 或单快照 > 500KB** → 改为按 entry 存差量 |
| 兼容性风险 | 低（纯增量）。唯一硬风险是 F8 静默截断，用清单化 `DOC_LIMITS` 一次性解决 |

## 3. 议题二：光照与视野墙（LOS）

业务问题：*我要给玩家出一张"他们看不到走廊尽头"的图；如果可以，拖动 token 时能立刻知道能看到哪。*

**CTO 判断（这句最贵）**：ClueForge 的产品定位是**编辑器/静态图工厂**，不是 VTT 运行时。FVTT 的 LOS 是"每个玩家客户端每帧按自己的 token 算"，那套东西的前提是有一个永远在跑的服务端+客户端。我们双击一个 HTML 文件，没有那个前提。所以 LOS 在本工具里只有两种合法形态：

- **A 档：离线算一次的"视野/暗区结果"**（导出图或预览图）——这是**贴合 FVTT 视觉结果**的做法；
- **B 档：编辑器内可实时预览的视野**——做得到，但要接受"拖动时降级、松手后重算"的体验，且必须设性能门禁。

### 3.1 数据模型改动（两档共用，全部 optional）

| 字段 | 说明 | 默认 |
| --- | --- | --- |
| `WallMeta.sight?: 'block' \| 'none'` | 这面墙挡不挡视线。生成器出的墙默认 `block` | `block` |
| `WallMeta.move?: 'block' \| 'none'` | 挡不挡移动（留给以后，先只存不算） | `block` |
| `DoorMeta.state?: 'closed' \| 'open'` | 门开着就不挡视线；`kind==='window'` 挡移动不挡视线，`secret` 两者都挡（与 FVTT 一致） | `closed` |
| `LightMeta {id,x,y,radius,color,intensity,flicker}` → `doc.lights?: LightMeta[]` | 独立光源；`radius` 用格数不用像素（换格大小时行为一致） | 空 |
| `MarkerMeta.vision?: { radius: number }` | token 自带视野半径（格） | 无 |
| `doc.lighting?: { enabled: boolean; darkness: 0..1; ambient: number }` | 全图暗度/环境光 | `enabled:false` |
| `doc.fogAreas?: { id, points: Pt[], mode: 'hide' \| 'reveal' }[]` | 手绘遮罩多边形（A 档的主要载体） | 空 |

墙体几何**不需要动**（F14：折线已经在手），门也不需要动——`kind` 已经能派生遮挡语义。**这是这项特性最幸运的地方：数据改动 < 1 人日，成本全在算法和渲染。**

### 3.2 两档

| | A 档：快（推荐先上） | B 档：对（单独立项） |
| --- | --- | --- |
| 方案要点 | 手绘雾多边形（`fogAreas`）+ "一键遮挡提示"：选中一个 token，按墙/门做**一次性**扇形遮挡计算，结果烘焙成多边形存进 `fogAreas`。渲染走第三个 canvas 层（复用 `gridCanvas` 的既有分层思路），暗色 `fill` + `destination-out` 挖洞；导出 PNG 时合成 | 真实可见性多边形：墙段空间索引（网格桶）+ 射线求交；多光源叠加、径向衰减、`flicker` 抖动；拖动时降级为"半径圆 + 半透明"，松手后重算 |
| 上线时间 | 4–6 人日 | 15–20 人日（拆三片：B1 单光源硬遮挡 5–7；B2 多光源+衰减+导出 5–7；B3 索引与门禁 3） |
| 一次性成本 | 低 | 高（唯一一项需要真算法工作的） |
| 每周期成本 | 0（烘焙后是纯几何） | 每次几何变更都要重建索引；关闭 `lighting.enabled` 时必须完全零开销 |
| 引入的技术债 | "阴影是快照不是实时"——用户改墙后雾不会自动跟着变。**利息：每次改墙后要手动重算一次，约 10 秒/次**；触发还债信号：用户抱怨"墙改了阴影没变" ≥2 次 | 高复杂度：缓存失效策略、降级路径、性能门禁都是长期负担 |
| 失败模式 | 雾多边形与 `doc.size` 缩放不一致（换 zoom 后雾错位）——雾坐标必须与墙一样用**文档像素绝对坐标**，不能跟着 zoom 走 | **内存悬崖**：`doc.size` 上限 10000×10000（F16），1:1 阴影画布 RGBA ≈ 400MB；导出 4x 直接爆。必须按"阴影层 ≤ 2048² 生成 + 拉伸"或分块，否则线上直接白屏 |
| 退出/迁移 | 关掉 `lighting.enabled` / 清空 `fogAreas` 即完全回退 | 同左 |

**推荐：先 A 档，B 档作为独立 ADR 立项，且必须先过性能门禁**（判据：40×30 格 + 300 段墙，重算 < 50ms，内存增量 < 80MB，关灯零开销）。过不了就停在 A 档——A 档已经能给玩家出"他们看不见走廊"的图，这是业务真正要的那一半价值。

## 4. 议题三：可复用素材库

业务问题：*我做了 60 个 NPC 头像，不想每张新图都重新上传一遍，也不想一个工程里塞 6MB 图导致文件传不动。*

当前是"资产嵌在文档里"（F10/F11）：好处是单文件可传播，坏处是**每张图重来一遍**，且多楼层会 ×N 膨胀（见 §5）。

| | A 档：快 | B 档：对（推荐） |
| --- | --- | --- |
| 方案要点 | 只做"本工程内复用"：`doc.assets`（≤40 张）出一个网格面板，点一下应用到选中标记；拖入即入库；hash 从 `长度_尾48` 换成 FNV-1a 64 位 | 独立的 `ClueForgeAssets` IndexedDB（**新库名，不升 `ClueForgeDB` 的版本**）+ 跨工程复用 + 用量显示（`navigator.storage.estimate()`）+ 配额上限（建议软 50MB）+ `.clueforge` 导出时只内嵌"本工程引用到的"子集 |
| 上线时间 | 3–4 人日 | 8–12 人日 |
| 一次性成本 | 低 | 中 |
| 每周期成本 | 0 | 库膨胀需人工清理；配额提示要设计（不能只剩"保存失败"） |
| 引入的技术债 | 复用半径只有"同一个工程"——**利息：每个新工程重新上传 20 张图，约 10 分钟** | 数据在浏览器里，清缓存/换浏览器即失。`file://` 下 IndexedDB 的 origin 行为需实测确认（当前自动存档已依赖它，属既有假设） |
| 失败模式 | hash 弱（F10）：两张**等长**且尾部 48 字符相同的 PNG 会被判为同一资产 → 换图串图。改 FNV-1a 后消失 | 引用完整性：`doc.markers[].assetId` 指向库里不存在的图 → 必须回退成占位矢量（现有 `applyMarkerImages` 已经有 `if (!asset) continue` 的兜底，可复用） |
| 退出/迁移 | 删面板即回退 | 删库需同步清 `assetId` 引用，否则一片空白棋子 |

**推荐 B 档，但分两步走**：先 A 档（3–4 人日，把 hash 修对 + 面板出来），再 B 档（库落地）。理由是 B 档真正的成本不在读取，而在**引用/去重/导出子集**三件事的口径，A 档会把这三件的接口先摸清楚。

**一票否决项**：`indexedDB.open('ClueForgeDB', 2)`。老 `project.js:52` 写死 `version 1`，库一旦升到 2，它打开就抛 `VersionError` → **自动存档静默失效**，用户以为在存其实没存。这是数据丢失级事故，只许新开库名（`ClueForgeAssets`）。

## 5. 议题四：多楼层

业务问题：*一栋三层小楼，我要三张图，还要能一键切换，最好楼梯能对上。*

**关键判断：楼层属于"工程"，不属于"地图文档"。** 理由：`导出 JSON / 导入 JSON` 是单图搬运（`ui.ts:422`），一张 JSON 里塞 N 层会把这个语义搞脏；而 `.clueforge` 是工程级信封，天然适合装楼层。

| | A 档：快（推荐） | B 档：对 |
| --- | --- | --- |
| 方案要点 | 工程层加 `project.mapStudioFloors: MapDoc[]`，**首层仍写 `project.mapStudio`**（旧版至少能看到一层，不崩）；编辑器加楼层条（F1/F2/…、新增、删除、复制到新层）；每层独立撤销栈（切层走现成的 `loadDoc(doc, false)`，历史不重置）；加 `project.savedBy: '0.8.x'` 用于"这文件被旧版存过、楼层可能已丢"的告警 | 文档内 `levels` + `version: 2`，楼梯/电梯作为跨层连接实体，跨层视野穿透、层间对齐参考线 |
| 上线时间 | 4–6 人日 | 15–25 人日（含迁移器与旧版拒读策略） |
| 一次性成本 | 低 | 高 |
| 数据模型改动 | 只动 `ClueForge/project.js`（新增字段 + 保存/恢复两处）与 `studio.ts` 加"换文档不换历史"的入口，`MapDoc` 零改动 | `MapDoc` 结构变更 + `validateMapDoc` 版本分支 + 迁移函数 + 所有渲染/回收路径复核 |
| 兼容风险 | 中：旧版重存会丢 `mapStudioFloors`（F13 实锤）→ 用 `savedBy` 探测并明确告警 | 高：`version: 2` 会被当前所有已分发的包**硬拒绝**（F7），等于逼所有协作者同时升级——对一个"双击就玩"的自用工具，这个代价不成比例 |
| 失败模式 | 资产按层重复存（每层 ≤6MB），5 层 = 30MB 文件，gzip 对 PNG 无效 → 传不动。**必须先做 §4 的 B 档（工程级资产池）再上多楼层** | 迁移不可逆（数据完整性红线） |
| 退出/迁移 | 删 `mapStudioFloors` 即回到单层；首层数据零损失 | 需要回滚脚本 + 备份纪律 |

**推荐 A 档，且严格排在素材库之后**：多楼层真正的隐藏成本是"资产 × 楼层数"，不是 UI。

## 6. 迭代路线（3 个迭代）

| 迭代 | 主题 | 内容 | 交付判据（可验收） | 不做的（明确划界） |
| --- | --- | --- | --- | --- |
| **0.8**<br>约 1.5 周 | 打地基 + 高感知小件 | ①版本号收口（package.json / main.ts / README 单一真源，注入 `__VERSION__`）②`DOC_LIMITS` 提为唯一真源（256px / 300KB / 6MB / 40 张 / noteChars）③`applyZOrder()` 消灭层序漂移 ④标记备注 ⑤标记 `z` + 上移/下移/置顶/置底 | 同一张图"画完立即看"与"存盘重开看"层序 100% 一致；备注 2000 字存盘重开一字不丢；`npm run build` 绿 | 不做图层面板；不做备注搜索 |
| **0.9**<br>约 2 周 | 资产与楼层 | ①素材库 A 档（面板 + FNV-1a 去重）②素材库 B 档（`ClueForgeAssets` 独立库 + 配额 + 导出只带引用子集）③工程级资产池（多楼层共享）④多楼层 A 档（`mapStudioFloors` + 楼层条 + `savedBy` 告警） | 60 张图跨 3 个工程复用零重传；3 层工程 `.clueforge` ≤ 8MB；旧包打开新工程不崩、且提示"楼层可能不完整" | 不做 `version: 2`；不做楼梯联动 |
| **0.10**<br>约 2–3 周 | 光照与视野 | ①墙/门遮挡语义字段 + 检查器开关 ②`fogAreas` 手绘雾 + 渲染层 + 导出合成 ③"按 token 烘焙一次遮挡" ④（可选，需过门禁）B 档单光源可见性 | 出图能表达"看不到走廊"；关灯零开销；10000px 图幅不白屏（阴影层 ≤2048² 生成） | 实时多光源、flicker、玩家客户端 |

**为什么是这个顺序**（Working Backwards 的倒推）：
1. **0.8 的每一条都是后面两件的地基**：`DOC_LIMITS` 单一真源 → 备注和楼层都要加限额；`applyZOrder` → LOS 覆盖层和素材库拖放都要插队到正确层；版本号收口 → 后面每次发版都要写"存档兼容说明"。
2. **0.9 内部必须素材库在前**：多楼层的成本被资产体积绑架。
3. **LOS 放最后**：它是唯一一项"做不完会变成半成品"的（性能悬崖 + 内存悬崖），也是唯一一项"业务价值只有一半需要实时"的。它必须具备"停在 A 档也算交付"的性质。

## 10. ADR（本轮 4 条，尽量短）

### ADR-001：存档兼容只保证"旧→新无损"，不保证"新→旧无损"
- 日期 2026-10-29 ｜ 状态：提议
- **当时的约束**：1 人维护；`project.js` 是"只做四处接线"的老模块，重存工程时重建固定字段（F13）；`validateMapDoc` 对 `version !== 1` 硬拒（F7）
- 备选与淘汰：①让旧版保留未知字段 → 需改老模块的收集逻辑，风险外溢到三个不相关模块；②bump `version: 2` → 所有已分发包拒读新档，协作半径内必须同步升级，不成比例
- 决定：新特性一律**增量 optional 字段**；`MapDoc.version` 停在 1，直到出现真正的破坏性变更；工程层加 `savedBy` 用于降级告警；旧版打开新档的承诺从"忽略新字段"降级为"不崩、不白屏"
- 已知代价：用旧包重存会丢新字段（含楼层）→ 靠告警 + README 纪律兜底
- 复审触发：出现第二个维护者，或出现真实的多版本协作场景

### ADR-002：楼层承载在工程层（`project.mapStudioFloors`），不进 `MapDoc`
- **约束**：`导出 JSON` 是单图搬运语义；`MapDoc` 被 `.clueforge` 与独立 JSON 两种入口共用
- 淘汰：文档内 `levels` —— 会让单图 JSON 变成"半个工程"，且需要 `version: 2`（撞 ADR-001）
- 决定：楼层是工程属性；首层双写 `mapStudio` 保证旧版可见
- 复审触发：需要楼梯联动/跨层视野穿透时

### ADR-003：素材库使用独立 IndexedDB（`ClueForgeAssets`），绝不升 `ClueForgeDB`
- **约束**：`project.js:52` 写死 `open('ClueForgeDB', 1)`
- 淘汰：升版本 + `onupgradeneeded` —— 老模块打开即 `VersionError`，自动存档静默失效（R1）
- 决定：新库名；`.clueforge` 仍只内嵌"本工程引用到的"资产子集，保住单文件承诺

### ADR-004：LOS 默认形态是"烘焙的静态视野"，实时视野是独立的、可被门禁否决的项目
- **约束**：无服务端、单文件双击；`size ≤ 10000²`；墙上限 2000×500 点
- 决定：0.10 先交付 `fogAreas` + 一次性遮挡烘焙；B 档（实时多边形）必须过"40×30 格 300 段墙 < 50ms / 内存 +80MB / 关灯零开销"三门禁
- 复审触发：门禁连续两次不过 → 放弃 B 档，A 档转正
